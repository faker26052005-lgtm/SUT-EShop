Cảm ơn. Bây giờ viết code cho PHẦN 1 của kế hoạch: các test thuộc xác thực (đăng ký, đăng nhập, quên và đặt lại mật khẩu), hồ sơ người dùng, sản phẩm, danh mục. Viết đầy đủ MỌI test của các nhóm này có trong kế hoạch, không bỏ test nào.

<helper_api>
Code chạy trong script Post-response của Postman, gồm các hàm async nhận tham số ctx. Có sẵn các công cụ sau:
- ctx.call(method, path, { token, body }) trả về Promise<{ code, json, text, ct }>. code là mã HTTP, json là body đã parse (null nếu không phải JSON), text là body dạng chuỗi, ct là Content-Type. token và body là tùy chọn; method viết hoa (GET, POST, PUT, DELETE).
- ctx.newUser(label) trả về Promise<{ email, password, id, token }>: tạo một người dùng mới, đăng nhập và trả về token. Dùng hàm này để mỗi test có dữ liệu riêng.
- ctx.ADMIN và ctx.USER: JWT của admin@eshop.com (Admin123!) và test@eshop.com (Test1234!), đã đăng nhập sẵn.
- ctx.RUN: chuỗi duy nhất của lần chạy, dùng để đặt tên dữ liệu bạn tạo ra.
- pm.test("T01 mô tả", function () { pm.expect(...) }) để kiểm tra; pm.expect(giá_trị, "mô tả").to... cho phép gắn mô tả vào thông báo lỗi.
Mọi lời gọi mạng đều phải dùng await.
</helper_api>

<examples>
Ba ví dụ mẫu về kiểu test mong muốn: (1) đường đi đúng kèm đọc lại sau khi ghi và dọn dữ liệu, (2) test âm tính kiểm cả mã lẫn nội dung lỗi, (3) kiểm trường KHÔNG được xuất hiện trong response. Chúng chỉ minh họa phong cách và mức độ chặt của assertion; đừng sao chép nội dung, hãy viết test cho kế hoạch của bạn.

```javascript
async function aiTests(ctx) {
  // Mục tiêu: xác nhận admin tạo được danh mục và danh mục xuất hiện trong danh sách (đọc lại sau khi ghi). SRS: FR-14
  const catName = "ZZ-" + ctx.RUN + "-cat";
  const created = await ctx.call("POST", "/api/categories", { token: ctx.ADMIN, body: { name: catName } });
  const list = await ctx.call("GET", "/api/categories");
  pm.test("T01 Admin tạo danh mục, danh sách trả về có danh mục vừa tạo", function () {
    pm.expect(created.code, "mã trạng thái khi tạo").to.equal(200);
    pm.expect(created.json.id, "id danh mục").to.be.a("number");
    pm.expect(list.json.some(function (c) { return c.id === created.json.id && c.name === catName; }), "danh mục có trong danh sách").to.equal(true);
  });
  await ctx.call("DELETE", "/api/categories/" + created.json.id, { token: ctx.ADMIN }); // dọn dữ liệu

  // Mục tiêu: thiếu token thì bị từ chối bằng 401 kèm thông điệp lỗi; token sai cũng bị từ chối. Tham chiếu: OWASP API2
  const noToken = await ctx.call("GET", "/api/cart");
  const badToken = await ctx.call("GET", "/api/cart", { token: "abc" });
  pm.test("T02 Giỏ hàng: không token trả 401 có thông điệp lỗi, token sai bị từ chối", function () {
    pm.expect(noToken.code, "không token").to.equal(401);
    pm.expect(noToken.json.error, "thông điệp lỗi").to.be.a("string");
    pm.expect(badToken.code, "token sai").to.be.oneOf([401, 403]);
  });

  // Mục tiêu: danh sách người dùng mà admin xem không được chứa dữ liệu nhạy cảm. Tham chiếu: OWASP API3
  const users = await ctx.call("GET", "/api/admin/users", { token: ctx.ADMIN });
  pm.test("T03 Danh sách người dùng của admin không chứa mật khẩu hay mã đặt lại", function () {
    pm.expect(users.code).to.equal(200);
    users.json.forEach(function (u) {
      pm.expect(u, "người dùng " + u.id).to.not.have.property("password");
      pm.expect(u, "người dùng " + u.id).to.not.have.property("reset_token");
    });
  });
}
```

Assertion YẾU (không chấp nhận): pm.expect(res.code).to.equal(200); vì chỉ biết máy chủ có trả lời, không biết nội dung đúng hay sai.
Assertion MẠNH (mong muốn): kiểm mã trạng thái, cấu trúc và giá trị trong body, đọc lại trạng thái sau khi ghi, kiểm trường không được xuất hiện.
</examples>

<rules>
1. Mỗi test kiểm tra hành vi ĐÚNG theo OpenAPI và SRS, không viết theo điều bạn đoán hệ thống đang làm. Hệ thống có thể chưa tuân thủ tài liệu.
2. Mỗi endpoint trong OpenAPI phải có ít nhất một test đường đi đúng và ít nhất một test âm tính hoặc bảo mật.
3. Dùng assertion mạnh: kiểm tra cả mã trạng thái lẫn nội dung body; sau thao tác ghi thì đọc lại để xác nhận; kiểm tra cả những trường KHÔNG được xuất hiện trong response. Assertion chỉ kiểm mã 200 là yếu, không chấp nhận.
4. Không thao tác phá hủy trên hai tài khoản mẫu: không đổi hồ sơ, vai trò, mật khẩu, không xóa, không đăng nhập sai trên admin@eshop.com và test@eshop.com. Mọi thay đổi dữ liệu dùng người dùng tạo bằng ctx.newUser hoặc dữ liệu có ctx.RUN trong tên, và dọn dữ liệu nếu có API xóa.
5. Khi tài liệu không nói rõ mã trạng thái, chấp nhận một tập mã hợp lý (ví dụ 400 hoặc 422) thay vì một mã duy nhất. Khi không chắc hành vi đúng là gì, ghi chú "// GIẢ ĐỊNH: ..." và không biến phỏng đoán thành kỳ vọng.
6. Mỗi test độc lập, không phụ thuộc thứ tự chạy của test khác.
</rules>
